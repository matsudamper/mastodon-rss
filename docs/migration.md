# マイグレーション

スキーマ変更は `backend/repository/src/main/resources/db/migration/` に
`V002__説明.sql` のような連番のファイルを足す。起動時に未適用のものが
バージョン昇順で適用され、適用済みのバージョンは `schema_version` テーブルに記録される。

ファイル名の一覧 (`db/migration/index`) は Gradle が生成するので、手で書く必要はない。
これは jar 内のディレクトリ走査が native-image で動かないことがあるため。

適用済みのファイルは書き換えないこと。チェックサムを記録しているので、
変更すると次の起動時にエラーになる。修正は新しい連番のファイルで行う。

## 手で書くのは SQL だけ

jOOQ の生成コードは SQL から自動で作られる。手順に codegen を叩く操作は無い。

ビルドすると次の順で走る。

1. `buildJooqSchema` が使い捨ての SQLite (`build/jooq/schema.db`) を作り直し、
   `db/migration` の SQL をバージョン昇順で全部適用する
2. `generateJooq` がその DB を読んで `build/generated/jooq` に Java を生成する
3. `compileKotlin` / `compileJava` が生成物を含めてコンパイルする

`compileKotlin` は生成タスクに依存しているので、SQL を足して普通にビルドすれば
テーブルの型は増えている。実行時の DB も、開発用のローカル DB も要らない。

生成コードは git に入れない。`build/` の下なので clone した直後は存在せず、
最初のビルドで作られる。CI も同じで、特別な手順は無い。

SQL を書き換えたときに生成物が古いままになることは無い（マイグレーションの
ディレクトリがタスクの入力として宣言されているので、変わればどちらも再実行される）。

## 生成の対象から外しているもの

`schema_version` は生成しない。`MigrationRunner` が自分で `CREATE TABLE` して
読み書きする管理表で、マイグレーション SQL には出てこない。
jOOQ から触れるようにすると、適用の記録を DSL 経由で書き換えられるようになってしまう。

マイグレーションの適用そのものも jOOQ を通さない。生成コードは
「適用し終わったスキーマ」から作られるので、適用する側がそれに依存すると
鶏と卵になる。`MigrationRunner` は素の JDBC のままにしてある。

現在のテーブル:

| テーブル | 内容 |
| --- | --- |
| `schema_version` | 適用済みマイグレーションの記録。バージョン・名前・チェックサム・適用日時 |
| `health_check` | 起動時の書き込み確認用。行は常に 1 件 |
