# マイグレーション

このディレクトリに置いた SQL が、スキーマの唯一の定義。
テーブルの型（jOOQ の生成コード）もここから作られる。

## 追加のしかた

`V002__説明.sql` のように連番のファイルを足す。手で書くのはこれだけで、
他に叩くコマンドは無い。

ファイル名は `V<連番>__<説明>.sql`。連番は 0 埋めの数字で、`MigrationLoader` が
ここから版を読む。この形になっていないファイルは起動時にエラーになる。

適用済みのファイルは書き換えないこと。内容のチェックサムを記録しているので、
変更すると次の起動時に落ちる。修正は新しい連番のファイルで行う。

## 適用のされかた（実行時）

起動時に、未適用のものが版の昇順で適用される。適用したファイルは
`schema_version` テーブルに版・名前・チェックサム・適用日時が記録される。
1 ファイル = 1 トランザクションなので、途中で失敗したファイルは丸ごと戻る。

ファイル名の一覧 (`db/migration/index`) は Gradle が生成するので手で書かない。
jar の中のディレクトリ走査は native-image で動かないことがあるため、
実行時はこの一覧を読んでファイルを開く。

`index` に載るのは `.sql` だけなので、このファイル (`README.md`) は
実行時には読まれない。

## 型が作られるまで（ビルド時）

jOOQ の生成コードは、ここの SQL から自動で作られる。codegen を叩く操作は無い。

1. `buildJooqSchema` が使い捨ての SQLite (`build/jooq/schema.db`) を作り直し、
   このディレクトリの SQL を昇順で全部適用する
2. `generateJooq` がその DB を読んで `build/generated/jooq` に Java を生成する
3. `compileKotlin` / `compileJava` が生成物を含めてコンパイルする

`compileKotlin` は生成タスクに依存しているので、SQL を足して普通にビルドすれば
テーブルの型は増えている。実行時の DB も、開発用のローカル DB も要らない。

生成コードは git に入れない。`build/` の下なので clone した直後は存在せず、
最初のビルドで作られる。CI も同じで特別な手順は無い。

このディレクトリがタスクの入力として宣言されているので、SQL を変えれば
スキーマの作り直しと codegen の両方が再実行される。生成物が古いまま残ることは無い。

実物の SQLite を経由するのは、生成される型を実行時の DB に合わせるため。
jOOQ には SQL を直接読む `DDLDatabase` もあるが、そちらは jOOQ 自身のパーサで
DDL を解釈するので、SQLite の型親和性まで一致する保証が無い。

## 生成の対象から外しているもの

`schema_version` は生成しない。`MigrationRunner` が自分で `CREATE TABLE` して
読み書きする管理表で、この下の SQL には出てこない。jOOQ から触れるようにすると、
適用の記録を DSL 経由で書き換えられるようになってしまう。

マイグレーションの適用そのものも jOOQ を通さない。生成コードは
「適用し終わったスキーマ」から作られるので、適用する側がそれに依存すると
鶏と卵になる。`MigrationRunner` は素の JDBC のままにしてある。
